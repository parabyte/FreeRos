Confirmed ROM structure
- 40100 is a 32 KiB blob.
- The first 16 KiB is a valid option ROM with signature 55 AA and size byte 0x20.
- The ROM header jump at C000:0003 targets C000:143F.
- The back half of 40100 contains tables/fonts and is extracted separately as 40100_tables.bin.

Confirmed integration points
- The ROM owns INT 10h video services.
- The ROM also installs or updates the legacy video vectors around IVT offsets 0x0040/0x0042 and 0x0108/0x010A/0x010C/0x010E.
- In the current C BIOS this matches the existing preservation of INT 10h, INT 1Dh, INT 1Fh, INT 42h and INT 43h after option ROM init.

Important BDA / low-memory state used by the ROM
- BDA 0x463 is read by the ROM.
- BDA 0x487 is heavily used as a control/status byte.
- BDA 0x488 is heavily used as a control/status byte.
- BDA 0x4A8 and 0x4AA are touched by the ROM.
- The ROM writes 0x64 to 0x487 at entry.
- The ROM repeatedly tests bit 1 of 0x487.
- The ROM masks and updates 0x488 in multiple places, so 0x488 is not just a passive mirror of generic BIOS state.

Interpretation of 0x487 / 0x488
- 0x487 and 0x488 appear to be PEGA-private extension bytes layered on top of the normal BDA.
- 0x487 likely contains feature and mode-state flags.
- 0x488 likely contains active display/adapter substate and is rewritten during mode handling.
- These bytes are important enough that leaving low memory dirty before PEGA init can break display bring-up.

Confirmed code patterns from the annotated ROM
- The ROM uses PIT channel 2 and port 0x61 during setup.
- It programs VGA/EGA-class ports including 0x03C0, 0x03C2, 0x03C4 and CGA/CRTC ports.
- It invokes INT 10h internally during its own logic instead of relying only on direct VRAM access.
- Text-related routines around C000:1204-C000:1264 use combinations of INT 10h AH=09h, AH=0Eh and AH=02h.
- There are substantial mode/table blocks from roughly C000:2061 onward.

Candidate under-documented / undocumented behavior
- The private use of BDA 0x487 and 0x488 appears more extensive than standard IBM-compatible BIOS documentation usually describes.
- The ROM appears to maintain its own higher-level display state in those bytes and then reflect or derive INT 10h behavior from them.
- The ROM installs/normalizes legacy video vectors itself, which means it assumes stronger ownership of the video stack than a minimal option ROM would.
- The ROM likely has PEGA-specific mode/state transitions that do not map 1:1 onto stock CGA/EGA text assumptions.

Current emulator findings from BIOS bring-up
- The custom FreeRos POST screen currently renders incorrectly in PCem.
- Observed failure pattern:
  - numeric fields render
  - filler characters such as '=' and '.' render
  - most labels do not render
  - the overall screen shape appears, but textual semantics are missing
- This strongly suggests our current custom POST rendering path is not aligned with the PEGA text subsystem expectations.
- A separate deployment mistake also occurred during testing: build/bios.bin was updated without regenerating the split PC1640 ROM files build/40043.v3 and build/40044.v3. That caused stale ROMs to be reinstalled until corrected.

What this implies for FreeRos
- FreeRos should stop treating PEGA as a generic "set mode and poke B800" adapter.
- FreeRos should prefer the actual PEGA INT 10h path and state model after option ROM init.
- FreeRos should preserve the PEGA-owned vectors exactly after video ROM initialization.
- FreeRos should not assume BDA 0x487 and 0x488 are disposable or generic.
- FreeRos should avoid custom POST layouts that depend on direct VRAM semantics until the PEGA mode/state rules are understood.

Most likely direction for fixing the current POST bug
- Revert to a conservative PEGA-compatible text output strategy.
- Let the option ROM establish the active text mode.
- Use basic INT 10h teletype or other ROM-owned text primitives for POST output first.
- Only add richer formatted screens after the PEGA mode tables and BDA extension bytes are decoded well enough to guarantee correct behavior.
